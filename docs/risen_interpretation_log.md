# RISEN Interpretation Log — GenieAI

เอกสารนี้ระบุรายละเอียดของระบบ **GenieAI** ตามกรอบ **RISEN Framework** (Role, Input, Scenario, Expectation, Number) เพื่อใช้เป็นบันทึกข้อตกลงและเป็นแนวทางหลักสำหรับ AI Agents ในการพัฒนาและตรวจสอบระบบ

---

## 1. Role (บทบาทของระบบ)
* **AI Business Assistant (เลขา AI อัจฉริยะ)**: ทำหน้าที่หลักเป็นเลขาตอบคำถาม ให้บริการข้อมูล และจองนัดหมายแทนเจ้าของธุรกิจ (ซาลอน คลินิกความงาม ร้านอาหาร) โดยสื่อสารกับลูกค้าอย่างเป็นมิตร สุภาพ และมีประสิทธิภาพผ่านทางแชต (LINE OA)
* **SaaS Admin Portal (ผู้ควบคุมระบบ)**: แพลตฟอร์มสำหรับเจ้าของร้านในการล็อกอิน อัปโหลดคู่มือธุรกิจ ตรวจสอบและบริหารจัดการคิวการจอง บริการ พนักงาน และดูบันทึกแชตของลูกค้าเพื่อทำการTakeover (ตอบกลับแทนบอต) ได้ทันที

---

## 2. Input (ข้อมูลนำเข้าของระบบ)
* **เอกสารคลังความรู้ (Knowledge Documents)**: คู่มือการให้บริการของร้านค้า เช่น รายการบริการ ราคา โปรโมชัน เงื่อนไข และ FAQ ในรูปแบบไฟล์ `.pdf`, `.txt`, หรือ `.md`
* **ประวัติและข้อความแชต (Customer Messages)**: ข้อความสนทนาที่ส่งมาจากลูกค้าผ่านแชนแนลต่างๆ (LINE Webhook หรือ Sandbox Chat) เพื่อใช้เป็นข้อมูลสืบค้นร่วมกับประวัติการคุยล่าสุดในระบบ Cache (Redis)
* **การจองนัดหมาย (Booking Requests)**: ข้อมูลส่วนตัวสำหรับการทำนัดหมาย ประกอบด้วย:
  1. ชื่อผู้ติดต่อ
  2. เบอร์โทรศัพท์
  3. อีเมล
  4. ประเภทบริการ / วันเวลาที่ต้องการนัดหมาย

---

## 3. Scenario (สถานการณ์การทำงานหลัก)
* **Scenario A: การอัปโหลดและวิเคราะห์คู่มือ (Onboarding & Manual Parsing)**: เจ้าของร้านอัปโหลดเอกสารระบบจะใช้ GPT-4o-mini Vision OCR แปลงภาพหรือข้อความและสกัดหัวข้อ (บริการ, โปรโมชัน, FAQ) มาจัดเก็บเป็นข้อมูลโครงสร้างธุรกิจ
* **Scenario B: การตอบคำถามด้วยคลังความรู้ (RAG & CAG Q&A)**: ระบบวิเคราะห์ขนาดคลังข้อมูล หากข้อมูลมีขนาดเล็กจะใช้ระบบ CAG (Context-based Answer Generation) ส่งข้อมูลทั้งหมดไปพร้อม Prompt หากเอกสารมีขนาดใหญ่จะใช้ระบบ RAG (Retrieval-Augmented Generation) ค้นหาเวกเตอร์ที่เกี่ยวข้องที่สุด 5 จุด จาก ChromaDB เพื่อนำไปตอบลูกค้า
* **Scenario C: การจองคิวอัตโนมัติ (Automated Booking Scheduling)**: เมื่อลูกค้าแสดงเจตจำนงในการจองคิว AI จะดึงเครื่องมือ (AI Function Calling) `check_booking_availability` เพื่อเช็คตารางและใช้ `create_booking` บันทึกนัดลงในไฟล์ JSON โครงสร้างระบบ
* **Scenario D: การควบคุมแทรกแซงแชต (Admin Live Chat Takeover)**: แอดมินร้านค้าสามารถเปิดหน้าจอ "Chat" เพื่อตรวจสอบประวัติสนทนาจริงของลูกค้า LINE และพิมพ์ข้อความตอบกลับโดยตรงผ่าน API ส่งไปยัง LINE อุปกรณ์ของลูกค้าทันที

---

## 4. Expectation (ความคาดหวังของผลลัพธ์)
* **การจำลองมนุษย์พิมพ์ข้อความ (LINE Multi-bubble & Delay)**: ระบบต้องแบ่งบับเบิลข้อความสนทนา (สูงสุด 5 บับเบิล) โดยเว้นจังหวะพิมพ์ (Typing Delay 2-4 วินาที) เพื่อความเป็นธรรมชาติ
* **ความถูกต้องในการนัดหมาย (No Double Bookings)**: การจองคิวต้องห้ามซ้อนทับกันเด็ดขาด (มีระยะเวลา Conflict 30 นาที) และต้องทำผ่าน AI Function Calling เท่านั้น
* **UI/UX มินิมอลพรีเมียม (Premium Aesthetics & Bilingual)**: หน้าแดชบอร์ดต้องรองรับการสลับภาษา (ไทย/อังกฤษ) และออกแบบด้วยโทนสี Navy-Blue-Cyan ที่มี Contrast สูง ตัวหนังสือคมชัด มีเอฟเฟกต์การเรืองแสง (Glow) และการเลื่อนพาร์ทเนอร์แบบ Seamless Loop

---

## 5. Number (ข้อจำกัดและตัวเลขสำคัญในระบบ)
| มิติระบบ | ขีดจำกัด / ค่าตัวเลข | คำอธิบาย |
|---|---|---|
| **CAG Token Threshold** | **15,000 Tokens** | จุดเปลี่ยนโหมด: น้อยกว่า 15K ใช้ CAG, มากกว่าใช้ RAG (ค้นหา Top-5 Chunks) |
| **Chat History Cache** | **10 Messages** | จำนวนประวัติการคุยล่าสุดต่อเซสชันที่เก็บไว้ใน Redis |
| **Session Cache TTL** | **2 Hours** | ระยะเวลาบันทึกประวัติการคุยของลูกค้าใน Redis |
| **Tenant Profile Cache** | **10 Minutes** | ระยะเวลาแคชข้อมูลโปรไฟล์ธุรกิจร้านค้าใน Redis |
| **Booking Conflict Window**| **30 Minutes** | หน้าต่างเวลาห้ามจองคิวซ้อนทับสำหรับพนักงานแต่ละท่าน |
| **Max LINE Bubbles** | **5 Bubbles** | จำนวนข้อความ LINE สูงสุดที่ระบบจะแยกส่งต่อการตอบกลับ 1 ครั้ง |
| **Human Typing Delay** | **2 - 4 Seconds** | เวลาจำลองการพิมพ์ข้อความก่อนส่งบับเบิลถัดไปทาง LINE |
| **API Ports** | **8000 (Backend) / 5173 (Frontend)** | พอร์ตเชื่อมต่อการรันระบบภายในเครื่อง |
